# jidouunten.jp プロダクト戦略

更新: 2026-09-07

市場・競合の根拠: [2026-09-07調査](../research/market-competition-20260907.md)。
JAMAの意向調査とメーカー・在庫検索・専門メディア・NASVAの比較から、初回公開は
日本仕様の販売単位と作動条件の横断比較に集中する。検索量や収益規模は未測定。
車種数より、同じ条件で候補を減らせることと、購入前の根拠確認を価値仮説とする。

初回リリースでGTM/GA4の同意後計測、GSC、Bing Webmaster Tools、sitemap登録も扱う。
公開後28日またはselector開始100セッションを初回評価の目安とし、未到達でも欠測と実測を報告する。
検索表示・クリック、結果0件率、比較・公式遷移を見て次Sprintを採択する。

## 1. 何を作るか

`jidouunten.jp` は、日本で入手・利用できる自動運転車と運転支援車を、
「レベル」と「実際に使える条件」から選ぶ意思決定ツールにする。

中心となる体験はニュースを読むことではない。利用者が次の問いに答えられることを成果とする。

> 自分の用途と道路環境では、どのレベル・どの車両・どの装備が候補になり、
> 何ができて何ができないのか。

## 2. 主な利用者とJob

| 利用者 | Job | 最初に必要な答え |
|---|---|---|
| 新車購入検討者 | 高速道路や渋滞時の負担を減らせる車を比較したい | 購入可能なLevel 1/2車と作動条件 |
| 先進機能を重視する買替層 | 現在の車より何が進化するか知りたい | ハンズオフ、車線変更、監視方式の差 |
| 自動運転に詳しくない人 | Level 2とLevel 3の違いを誤解なく知りたい | 誰が周囲を監視し、誰が責任を持つか |
| 技術・事業の調査者 | 国内の実用化状況を追いたい | 市販車、移動サービス、実証の区別 |

最初のMVPでは「日本で個人が選べる乗用車」を主対象にする。Level 4/5の移動サービス・実証は、
購入可能な車両と混ぜず別区分で示す。

## 3. 中核導線

```text
レベルを選ぶ
  → そのレベルで可能なこと・運転主体を理解する
  → 購入可能な車両を絞る
  → 道路・速度・監視・装備・価格帯で比較する
  → 公式情報と販売状態を確認して候補を決める
```

トップページの第一CTAは「レベルから車を選ぶ」。その後に、利用シーンから探す、車種比較、
基礎解説を置く。検索流入した解説やニュースからも、必ず該当レベル・車種の選択画面へ戻す。

## 4. 比較軸

レベルは入口だが、同じレベル内の差を隠さない。最低限、次を比較可能にする。

- 自動化レベルと運転主体
- 対象道路、速度域、天候などのODD（作動設計領域）
- ハンズオフ可否、視線・ドライバー監視、引継ぎ要求
- 車線維持、追従、車線変更、渋滞対応、駐車などの機能
- 必須グレード、メーカーオプション、サブスクリプション
- 日本での販売状態と確認日
- メーカー公式ページ、取扱説明書、国土交通省情報へのリンク

## 5. 信頼設計

- Level 1–2は「運転支援」、Level 3以上を「自動運転」と明記する。
- Level 2では運転者が常時監視することを比較カードと詳細ページで隠さない。
- メーカーの機能名称と自動化レベルを同一視しない。
- 不明は `unknown`、情報が古い場合は `stale` と表示し、推測で補完しない。
- 「搭載あり」ではなく、モデル年・グレード・必要装備・日本仕様まで特定する。
- 安全性の断定や事故回避の保証はしない。購入・使用前に公式説明と取扱説明書の確認を促す。

## 6. コンテンツと集客

ニュースはサブ導線とし、以下のいずれかを満たすものだけ扱う。

1. 車両・グレード・機能・販売状態のデータ更新につながる。
2. 法制度や自動化レベルの理解を更新する。
3. 比較・選択の新しい需要を検証できる。

速報本数やPVだけを目標にしない。記事から関連車両、レベル、比較へ遷移した率を評価する。
恒常的な検索流入は「Level 2 ハンズオフ 車種」「渋滞 自動運転 車」などの選択意図を持つ
解説・比較ページで獲得する。

## 7. 収益仮説

優先順は以下。利用者の判断を歪めないことを前提に検証する。

1. ディーラー・一括見積・中古車在庫への送客
2. 保険、充電、カーリース等の周辺サービス送客
3. 法人向けデータ提供または比較ウィジェット
4. 補助的な広告

広告表示量ではなく、比較完了率、公式・販売先への遷移率、再訪率、送客成果を主要KPIにする。

## 8. MVPと段階展開

### Sprint 1 — Level-first selector

- Level 1/2/3を誤解なく説明する
- 公式一次情報で確認した日本向け車両レコードを最低6件掲載する
- レベル、道路、ハンズオフ可否、販売状態で絞り込める
- 車両詳細で条件、必要装備、根拠、確認日を表示する
- 比較対象を2台まで並べられる
- Cloudflare PagesのpreviewでE2E確認し、本番公開可能にする

### 次の段階

- Sprint 2: 用途質問から候補を返すガイドと比較表の深化
- Sprint 3: 更新日・販売状態の監視、差分レビュー、データ鮮度表示
- Sprint 4: 送客導線と計測（比較完了→公式/販売先遷移）
- Sprint 5: 車種データに接続する解説・ニュース
- Sprint 6: 利用実績を基に保存比較、通知、Level 4サービスを判断

順番は固定ロードマップではない。GitHub ProjectのReadyキューと実測に基づき更新する。

## 9. 技術方針

- Astro + TypeScript、static-first
- 車両データはGit管理の構造化データ + schema validation
- 絞り込みと比較は初期はクライアント内で完結
- 初回はCloudflare Pages Direct Uploadで公開する。GitHubはソース・Sprintの正本とする。
- 自動配信は次の運用課題。Direct UploadプロジェクトはGit連携へ切替できないため、
  GitHub ActionsからWranglerで配信する方式を優先検討する（専用token・repository secretの設定が必要）。
- フィードバック保存や管理画面が必要になった時点でPages Functions / Workers / D1を検討

Cloudflareは新規アプリではWorkersを主軸に案内しているが、MVPは静的比率が高く、ユーザー希望にも
合うためPagesを採用する。動的要件が増えた時にWorkersへ移れる境界を保つ。

## 10. 成功・失敗の判定

初期KPI:

- selector開始数 / 到達セッション
- 絞り込み完了率
- 比較開始率・比較完了率
- 車両詳細→メーカー公式/販売先クリック率
- 根拠が期限内に確認された車両レコード率

失敗兆候:

- 記事PVは増えるがselector利用が増えない
- 「Level 2だから自動運転」と誤認させる
- 車種名だけでグレード・装備・作動条件が不明
- 更新日がなく、販売終了車と購入可能車が混在する
- データ保守よりニュース量産へ作業が偏る
